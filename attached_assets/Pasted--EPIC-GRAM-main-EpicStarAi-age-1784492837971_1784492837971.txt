# 🔴 Критические проблемы

## 1. `/api/operator/command` не проверяет пользовательскую сессию

В начале маршрута отсутствует вызов вроде:

```ts
requireSession()
getAuthenticatedUser()
resolveTelegramBinding()
```

Маршрут сразу принимает JSON из браузера и начинает обработку команды. fileciteturn8file0L66-L80

Это означает, что безопасность AI-оператора сейчас не соответствует безопасности `/api/telegram/*`.

### Риск

Пользователь или внешний запрос потенциально может обращаться к оператору без корректной EPICGRAM-сессии, если маршрут доступен через nginx.

### Исправление

Каждый операторский маршрут должен:

1. Проверять `epic_session`.
2. Получать `userId` только из серверной сессии.
3. Получать Telegram binding только из БД.
4. Возвращать `401`, если сессии нет.
5. Возвращать `409 no_binding`, если Telegram не подключён.

---

## 2. `accountId`, `chatId` и история принимаются от браузера

Маршрут берёт:

```ts
tg.accountId
body.accountId
tg.chatId
body.chatId
body.messages
```

непосредственно из запроса клиента. fileciteturn8file0L80-L113

Это нарушает основной принцип изоляции:

> Браузер не должен определять, каким Telegram-аккаунтом управляет оператор.

### Риск

Можно подменить:

- `accountId`;
- `chatId`;
- название чата;
- историю сообщений;
- целевой канал публикации.

Даже если отправка пока заблокирована, AI может анализировать подложный контекст и создавать действие для чужого target.

### Правильная схема

Браузер передаёт только:

```json
{
  "command": "Подготовь ответ",
  "chatId": "123"
}
```

Сервер:

```text
session → userId → telegramBinding → accountSlot
        → проверка принадлежности chatId
        → чтение реальной истории через TDLib
        → AI
```

`accountId` из браузера должен полностью игнорироваться.

---

## 3. Operator API не передаёт identity пользователя в backend

Запросы к:

```text
/ai/route
/ai/suggest
```

содержат `chatId`, `chatTitle`, `command`, `messages`, но не содержат подтверждённый сервером `userId`, `bindingId` или `accountSlot`. fileciteturn8file0L140-L155 fileciteturn8file0L318-L329

### Последствие

Backend не может надёжно определить:

- кому принадлежит команда;
- какой TDLib-slot разрешён;
- имеет ли пользователь доступ к чату;
- где хранить корректный audit log.

Это главный архитектурный разрыв между **AI-оператором** и **мультипользовательским Telegram-клиентом**.

---

## 4. `publish_post` доверяет выбранному браузером `chatId`

В коде прямо указано, что публикация привязывается к «выбранному оператором» `chatId`. fileciteturn8file0L185-L230

Но сам `chatId` выше получен из тела запроса, а не проверен через серверный TDLib-slot.

### Требование

Перед созданием approval-карточки сервер обязан выполнить:

```text
assertChatBelongsToAccount(userBinding.accountSlot, chatId)
```

Без этого approval gate защищает только от случайного клика, но не от подмены target.

---

## 5. Планировщик фактически отсутствует

Маршрут прямо возвращает:

> `schedule_post: blocked — no executor`

То есть AI может предложить расписание, но ничего реально не ставится в очередь. fileciteturn8file0L233-L256

Следовательно, сейчас отсутствуют:

- очередь заданий;
- scheduled jobs;
- retry;
- статусы публикации;
- отмена задачи;
- история автопостинга;
- защита от повторной отправки.

# 🟠 Средние проблемы

## 6. Middleware проверяет только наличие cookie

Middleware сознательно проверяет не валидность, а только наличие `epic_session`. Это допустимо как первый слой, но только при условии, что каждый API handler проводит полноценную проверку. fileciteturn5file0L16-L21

Проблема в том, что `/api/operator/*` вообще не включён в matcher:

```ts
matcher: [
  "/client/:path*",
  "/api/telegram/:path*",
  "/api/v1/telegram/:path*"
]
```

fileciteturn5file0L46-L48

### Нужно добавить

```ts
"/api/operator/:path*",
"/api/operator-events/:path*",
"/api/ai/:path*"
```

Но middleware не заменяет серверную проверку внутри route handler.

---

## 7. Ошибки backend часто возвращаются с HTTP 200

Например, при отсутствии выбранного чата маршрут возвращает:

```json
{
  "ok": false,
  "error": "no_active_chat"
}
```

с HTTP `200`. fileciteturn8file0L115-L130

Ошибки Tool Router также маскируются под `200`. fileciteturn8file0L280-L295

### Почему это плохо

- мониторинг считает запрос успешным;
- frontend сложнее отличает ошибку от результата;
- nginx и observability не видят деградацию;
- сложнее писать интеграционные тесты.

### Нормальные статусы

| Ситуация | HTTP |
|---|---:|
| Нет сессии | 401 |
| Нет binding | 409 |
| Чужой chat/account | 403 |
| Нет выбранного чата | 400 |
| AI backend offline | 503 |
| Timeout | 504 |
| Некорректная команда | 422 |

---

## 8. Intent router построен на регулярных выражениях

Команды определяются набором regex:

```ts
/послед.*сообщ/
/суммар|summar|summary/
/подготов.*пост/
/конкурент/
/расписан/
```

fileciteturn8file0L34-L46

Это пригодно как временный fallback, но будет ошибаться на естественных формулировках.

Например:

- «Посмотри, что обсуждали вчера»;
- «Ответь человеку вежливо»;
- «Сделай публикацию из этого текста»;
- «Ничего не отправляй, просто покажи вариант».

Нужен структурированный planner с JSON Schema и policy validation после модели.

---

## 9. Frontend передаёт историю сообщений модели

Сейчас последние 20 сообщений могут поступать из браузера. fileciteturn8file0L107-L136

Правильнее читать сообщения сервером через TDLib. Иначе возможны:

- подмена контекста;
- устаревшие сообщения;
- неполная история;
- смешение чатов;
- prompt injection через клиентский payload.

# 🟢 Что уже сделано правильно

## Защита `/client`

Middleware перенаправляет пользователя без cookie на `/login` и запрещает кэширование приватного контента. fileciteturn5file0L25-L43

## Отдельная EPICGRAM-сессия

Последний commit добавляет предварительную EPICGRAM-авторизацию до Telegram binding и исправляет цикл `/login ↔ /client`. fileciteturn2file0

## Safe Mode

AI-оператор по умолчанию работает как `READ_ONLY`, а отправка требует ручного подтверждения. fileciteturn8file0L163-L181

## Нет прямого auto-send

Ответы явно содержат:

```json
{
  "can_send": false,
  "auto_send": false,
  "bulk_actions": false
}
```

Это правильный режим для текущего этапа.

## AI умеет разделять типы задач

Уже предусмотрены:

- чтение последних сообщений;
- анализ чата;
- подготовка ответа;
- подготовка поста;
- анализ конкурентов;
- контент-план;
- предложение расписания.

Структурно это хорошая база, но executor и identity propagation ещё не завершены.

# Что проверяем в live-аудите

## P0 — безопасность

1. Открыть `/client` без cookie.
2. Вызвать `/api/operator/command` без cookie.
3. Подставить случайный `accountId`.
4. Подставить чужой `chatId`.
5. Подставить NOVIKOVA slot от другого пользователя.
6. Проверить logout и повторное использование cookie.
7. Проверить два браузера и два пользователя одновременно.
8. Проверить прямые запросы к порту `8788`.

## P1 — Telegram

1. Новый пользователь без binding.
2. QR-авторизация.
3. Телефон → код → 2FA.
4. Перезапуск PM2.
5. Проверка сохранения binding.
6. Список чатов.
7. История сообщений.
8. Каналы, группы, личные сообщения.
9. Медиа и вложения.
10. Logout только текущего пользователя.

## P1 — AI-оператор

1. Подготовить ответ.
2. Проанализировать чат.
3. Найти сообщения без ответа.
4. Подготовить пост для выбранного канала.
5. Переключить чат во время генерации.
6. Проверить, что target не изменился.
7. Подтвердить отправку.
8. Отменить отправку.
9. Повторно нажать подтверждение.
10. Отключить AI backend и проверить корректную ошибку.

# Приоритет исправлений

## P0 — блокирует публичный запуск

1. Добавить auth guard во все `/api/operator/*`.
2. Полностью игнорировать клиентский `accountId`.
3. Резолвить Telegram account slot через серверную сессию.
4. Проверять принадлежность `chatId` текущему slot.
5. Читать историю сообщений сервером.
6. Передавать в backend подписанный execution context.
7. Закрыть прямой доступ к backend `8788`.

1. Реальный send executor после approval.
2. Idempotency key для каждой отправки.

4. Очередь scheduled posts.
5. Retry и dead-letter queue.
6. Статусы задач в интерфейсе.
7. End-to-end тест двух пользователей.

## P2 — продуктовый UX

1. Убрать технические формулировки.
2. Показать понятные состояния подключения.
3. Единый русский интерфейс.
4. Разделить «анализ», «черновик», «действие».
5. Показывать точный аккаунт и чат перед подтверждением.

# Заключение

**Клиент уже не является пустым макетом.** Есть реальная EPICGRAM-сессия, TDLib-flow, чатовый интерфейс, AI routing и approval mode.

Но сейчас существует критический разрыв:

> Telegram API начали делать account-aware, а AI-оператор ещё доверяет данным из браузера.

До закрытия этого разрыва EPIC☠️GRAM нельзя безопасно открывать внешним пользователям. Оптимальный следующий этап — **P0 Operator Identity & Target Isolation Audit**, затем полноценный live smoke-test на двух независимых аккаунтах.
